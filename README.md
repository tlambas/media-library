# Media Library API

A Java/Spring Boot REST API for managing a personal collection of movies, albums, and songs. This is an **educational backend project**, built to learn the Spring ecosystem and practice application security, HTTP error handling, concurrency, and cloud-architecture concepts.

My professional background is primarily in C#/.NET. I wrote most of this project myself while using ChatGPT as a learning guide, including for feedback and assistance with some tests. The goal was to implement and understand the concepts—not to present this as a production-ready application.

## Technology stack

- Java 25 and Gradle (wrapper included)
- Spring Boot 4.1.1, Spring Web MVC, Spring Security
- Spring Data JPA / Hibernate and MySQL
- HTTP Basic authentication and BCrypt password hashing
- Jakarta Bean Validation and Spring `ProblemDetail`
- JUnit, Spring Boot Test, MockMvc, and Spring Security Test

## Architecture

```text
HTTP client
    |
Controller  <-- Request / response DTOs
    |
Service     <-- Application logic, ownership checks, transactions
    |
Repository  <-- Spring Data JPA
    |
MySQL
```

The `controller` package exposes endpoints and centralizes exception handling; `service` implements operations and authorization checks; `repository` handles persistence; `model` contains JPA entities and the `MediaType` enum; `DTO` contains request and response representations; and `config` contains Spring Security configuration.

A media item has a title, description, media type (`MOVIE`, `ALBUM`, or `SONG`), an owner, timestamps, and a JPA-managed version field.

## API endpoints

All media-item endpoints require authentication. Media items are scoped to the authenticated owner.

| Method | Endpoint | Description |
| --- | --- | --- |
| `POST` | `/api/media-items` | Create an item owned by the authenticated user |
| `GET` | `/api/media-items/{id}` | Retrieve an owned item |
| `GET` | `/api/media-items/` | List the authenticated user's items |
| `PUT` | `/api/media-items/{id}` | Update an owned item, supplying its current `version` |
| `DELETE` | `/api/media-items/{id}` | Delete an owned item |
| `GET` | `/api/whoami` | Return the authenticated username |
| `GET` | `/api/test-error` | Learning-only endpoint for testing error handling |

Example creation request (using HTTP Basic authentication):

```http
POST /api/media-items
Content-Type: application/json

{
  "title": "Inception",
  "description": "Science fiction film",
  "type": "MOVIE"
}
```

A successful creation returns `201 Created` with an ID and a version (initially `0`). The server assigns the owner from the authenticated user; the client cannot set it through the request DTO.

To update an item, send `PUT /api/media-items/{id}` with the editable fields and the version from the latest response:

```json
{
  "title": "Inception (2010)",
  "description": "Science fiction film",
  "type": "MOVIE",
  "version": 0
}
```

A stale version is rejected with `409 Conflict` rather than silently overwriting a newer update.

## Application security

- **Authentication:** Spring Security authenticates against users stored in MySQL; passwords are BCrypt-hashed.
- **Ownership-based authorization:** Read, list, update, and delete operations are constrained by the authenticated username. An item that is absent or belongs to someone else is treated as not found.
- **Mass-assignment protection:** Request DTOs do not expose ownership, so clients cannot reassign items by including an `owner` property.
- **Response safety:** The media-item response DTO contains media-item data rather than serializing the `User` entity or its password hash.
- **Verification:** Integration tests cover authentication, user isolation, and attempted ownership manipulation.

**Security limitations:** HTTP Basic and disabled CSRF protection were chosen for local API experimentation; the setup is not hardened for browser-based production use. `/api/test-error` is a public learning endpoint and should be removed or restricted outside this exercise.

## HTTP errors and validation

A global `@RestControllerAdvice` returns structured `ProblemDetail` responses.

| Situation | HTTP response |
| --- | --- |
| Invalid input (for example, a blank title) | `400 Bad Request` |
| Missing or invalid credentials | `401 Unauthorized` |
| Insufficient role permissions | `403 Forbidden` |
| Item missing or not owned by requester | `404 Not Found` |
| Stale version / optimistic locking conflict | `409 Conflict` |
| Unexpected server error | `500 Internal Server Error` |

Unexpected errors are logged while clients receive a generic error description. The request DTO currently validates the title with `@NotBlank`; further field constraints could be added as the API evolves.

## Concurrency and optimistic locking

I practiced Java concurrency separately under `src/test/java/practice/`, exploring lost increments, `synchronized`, `AtomicInteger`, and `CountDownLatch`.

In the API, `MediaItem` uses JPA's `@Version` for optimistic locking. The update service compares the client-supplied version with the current entity version, and Hibernate also detects competing database updates. Conflicts are mapped to `409 Conflict`, allowing the client to reload the latest state before trying again. Tests exercise stale-client updates and concurrent database transactions.

A key lesson was that `synchronized` only coordinates threads sharing a JVM lock; it cannot protect a shared database across multiple application instances. Database-level concurrency control is needed for that scenario.

## Running locally

**Prerequisites:** JDK 25, MySQL, and a terminal. Use the included Gradle wrapper; a system Gradle installation is not required.

Create a development database (for example, `media_library`) and a **separate, disposable** test database (for example, `media_library_test`). Grant the configured MySQL user the appropriate permissions.

Set these environment variables before starting the application:

| Variable | Example value | Purpose |
| --- | --- | --- |
| `DB_URL` | `jdbc:mysql://localhost:3306/media_library` | Development JDBC connection |
| `DB_URL_TEST` | `jdbc:mysql://localhost:3306/media_library_test` | Test JDBC connection |
| `DB_USERNAME` | `media_library_app` | MySQL username |
| `DB_PASSWORD` | *(your local password)* | MySQL password |

For example, in PowerShell (replace the password with your own):

```powershell
$env:DB_URL = "jdbc:mysql://localhost:3306/media_library"
$env:DB_URL_TEST = "jdbc:mysql://localhost:3306/media_library_test"
$env:DB_USERNAME = "media_library_app"
$env:DB_PASSWORD = "<local-password>"
.\gradlew.bat bootRun
```

The API listens at `http://localhost:8080` by default. The application does **not** seed demonstration users in the default profile. The `test` profile supplies test accounts for automated tests. To call authenticated endpoints manually, create an application user with a BCrypt-encoded password in your local database or add a development-only seeding mechanism.

Run the tests on Windows:

```powershell
.\gradlew.bat clean test
```

On macOS/Linux:

```bash
./gradlew clean test
```

**Important:** The test profile uses `spring.jpa.hibernate.ddl-auto=create-drop`. Only point `DB_URL_TEST` at a dedicated disposable database, since the test schema will be created and dropped. The development profile currently uses Hibernate `ddl-auto=update`, which is convenient for learning but should be replaced with managed migrations in production.

## Testing

Spring Boot integration tests use MockMvc and a separate MySQL test database to check authentication, authorization, ownership assignment, request validation, and concurrency behavior. There are also small standalone Java concurrency exercises. The tests demonstrate both expected success paths and rejected operations, including stale updates.
